# 측정 계획

## 이 실험이 답하려는 질문

**Re-ranking, Sentence Window Retrieval, Contextual Compression, HyDE, Query
Rewriting 다섯 기법이 온디바이스 SLM 환경에서 효과적인가.**

"SLM이 근거를 읽고 추론할 수 있는가"는 이 실험의 주장이 아니라 **전제조건**이다.
주장은 어디까지나 다섯 기법에 관한 것이고, 아래의 모든 설계는 그 주장을 측정
가능하게 만들기 위해 존재한다.

## 첫 번째 시도가 답을 내지 못한 이유

2026-08-01 run은 중단되기 전까지 SciFact에서 `none`과 `query_rewrite`를 완주했다.
두 모드는 어떤 지표에서도 분리되지 않았다. 원인이 셋인데 그중 어느 것도
"기법이 효과가 없다"가 아니다.

1. **기법이 실행되지 않았다.** `query_rewrite`에서 재작성된 질의가 원본과
   **바이트 단위로 동일한 것이 300건 중 252건(84%)**이었다. 그 행들은 `none`과
   완전히 같은 검색을 수행했다. 그런데 `transform_used_fallback`은 0으로 집계됐다 —
   출력이 원본과 같은 것을 실패로 치지 않기 때문이다. 즉 48건을 재작성하고
   300건 성공으로 보고했다.

2. **생성기가 컨텍스트를 무시한다.** 지금까지 시험한 모든 후보가 근거와 무관하게
   같은 답을 낸다 (`generation_quality_2026-08-02.md` 참조). 게다가 다섯 기법 중
   셋이 **바로 그 생성기를 호출해 구현되어 있다.** 생성기의 약점은 최종 답변에만
   국한되지 않는다.

3. **기준선이 없다.** 바닥과 천장이 없으면 분모가 없다. 0.5965 → 0.599라는 차이를
   크다고도 작다고도 없다고도 판정할 수 없다.

## Layer 0 — 위생 점검: 기법이 실제로 실행됐는가

어떤 품질 지표보다 먼저 보고한다. 조용히 아무 일도 안 한 기법이 섞여 있으면
그 아래의 모든 숫자가 무의미해진다.

| 기법 | 실행됐다고 볼 조건 | 현재 상태 |
|---|---|---|
| Query Rewriting | 재작성 질의 ≠ 원본 | **16%** (48/300) |
| HyDE | 생성 문서가 질의의 재진술이 아님 | 미측정 |
| Contextual Compression | 압축 결과 ≠ 입력 컨텍스트 | 미측정 |
| Re-ranking | 최종 top-k 순서 ≠ 검색 순서 | 미측정 |
| Sentence Window | 확장된 청크 ≠ 원본 청크 | 미측정 |

`sanitizeQueryRewrite`와 같은 계열 함수들이 **변화 없음(no-op)을 성공·폴백과
구분되는 제3의 상태로** 집계해야 한다.

## Layer 1 — 기준선: 측정 가능한 폭이 얼마나 되는가

다섯 기법은 전부 아래 두 조건 사이의 구간에서 경쟁한다. 이 구간이 0이면 어떤
기법도 효과를 드러낼 수 없고, 실험은 신호를 만들어낼 수 없다.

| 조건 | 생성기에 주는 컨텍스트 | 의미 |
|---|---|---|
| **closed-book** | 없음 | 바닥 — 검색 없이 모델이 아는 것 |
| **retrieved** | 실제 검색 결과 (현행) | 지금 구축된 시스템 |
| **oracle** | gold 근거만 | 천장 — 검색이 완벽할 때 |

효과 크기는 원시 차이가 아니라 `oracle - closed-book` 대비 비율로 보고한다.

구현 비용은 작다. `buildPrompt(query, contexts)`가 컨텍스트가 들어가는 유일한
지점이고, 모든 레코드에 `reference_contexts`가 이미 들어 있다(SciFact 300/300건).
closed-book은 빈 벡터를, oracle은 gold 청크를 넘기면 된다.

**closed-book을 먼저 돌렸다면 생성기 문제를 14시간이 아니라 1시간 만에 알았다.**

## Layer 2 — 각 기법을 실제로 작동하는 층위에서 평가한다

다섯 기법은 개입하는 층이 다르다. 하나의 파이프라인에 몰아넣고 같은 지표로
채점하면 서로 다른 것을 뒤섞게 된다.

**검색 층위 기법** — *어떤 문서가 오는지*를 바꾼다. 실제 검색 조건에서 BEIR
지표로 측정하며, 생성기가 필요 없다.

- Query Rewriting
- HyDE

**컨텍스트 층위 기법** — 주어진 후보 풀에서 *생성기가 무엇을 보는지*를 바꾼다.
검색 변동성이 효과를 가리지 않도록 통제된 컨텍스트에서 측정한다.

| 조건 | 후보 풀 구성 |
|---|---|
| A | gold 청크만 |
| B | gold + 방해 청크 k개, 위치와 개수를 통제 |
| C | 방해 청크만, gold 없음 |
| D | 컨텍스트 없음 (공통 바닥선) |

- Re-ranking — 조건 B에서 gold를 방해 문서 위로 끌어올리는가
- Sentence Window
- Contextual Compression

조건 B가 정작 흥미로운 질문이 있는 자리다. **SLM이 컨텍스트 잡음을 어디까지
견디는가, 그리고 어떤 기법이 그것을 얼마나 복구하는가.** 다섯 모드의 순위표보다
온디바이스 논문에 어울리는 질문이다.

`rerank_candidate_k`가 9, `top_k`가 3이므로 후보 풀 크기는 기존 설정을 그대로 쓴다.

## Layer 3 — 지표

**만들어야 할 것. 지금 존재하지 않으며, 이것 없이는 질문에 답할 수단이 없다.**

- SciFact: `response`에서 라벨을 파싱해 gold 대비 macro-F1을 계산한다. test 300건
  중 188건이 SUPPORT/CONTRADICT 메타데이터를 갖고, 나머지 112건은 근거 필드가
  비어 있다는 규약에 따라 NOINFO다.
- NQ: gold 짧은 정답 대비 Exact Match와 토큰 F1. **BEIR 변환본에는 정답 문자열이
  아예 없다.** 질문 텍스트를 `nq_open`과 대조해 352/500건(70%)을 복구했고, 나머지는
  train 전체 split이 필요하다.

**유지할 것.** BEIR precision / recall / nDCG / MAP / MRR. qrels로 정확히 계산되고
무료이며 재현 가능하다.

**주 실험에서 뺄 것.** RAGAS `context_precision`과 `context_recall`은 BEIR를
중복하면서 더 느리고 유료이며 심판 모델에 의존한다.

| | BEIR | RAGAS |
|---|---|---|
| none | ndcg@3 0.598 | context_precision 0.592 |
| none | recall@3 0.661 | context_recall 0.629 |
| query_rewrite | ndcg@3 0.600 | context_precision 0.605 |
| query_rewrite | recall@3 0.665 | context_recall 0.625 |

**나중으로 미룰 것.** RAGAS `faithfulness`와 `answer_relevancy`는 생성기를 재는
지표이므로, 생성기가 컨텍스트에 반응하기 전까지는 정보를 담지 않는다. 나중에
부분표본으로 부차 보고할 가치는 있다.

비용은 RAGAS가 지배한다. `none`이 4.5시간, `query_rewrite`가 5.0시간 걸렸고
(각 300문항) 거의 전부가 judging이다. RAGAS를 빼면 12개 run 전체가 80시간이 아니라
**10시간 이내**에 끝난다.

## 미결 사항

- **생성기.** 후보 넷이 근거 민감도 대조를 통과하지 못했다 (gemma-3-270m,
  SmolLM2-360M, Qwen3-0.6B, Qwen3-1.7B). Layer 1이 있으면 후보 선정이 측정으로
  바뀐다 — **쓸 수 있는 모델이란 oracle이 closed-book과 벌어지는 모델**이다.
  그런 모델이 나올 때까지 컨텍스트 층위 기법 둘과 end-task 지표 둘이 막힌다.
  검색 층위는 막히지 않는다.
- **NQ 코퍼스.** BEIR 원본 2,681,468건 중 20,623건(0.77%)만 쓰고 있어 인용한
  벤치마크보다 검색이 쉽다. 방해 문서 풀을 키우든지, 부분표본임을 명시하고
  타 논문과의 직접 비교를 포기하든지 정해야 한다.
- **범위.** 예산 안에서 생성기를 해결하지 못하면 검색 층위 결과만으로도 독립적인
  기여가 되고, 컨텍스트 층위 기법들은 조용한 공백이 아니라 명시된 한계가 된다.

## 작업 순서

1. Layer 0 위생 카운터 — 가장 싸고, 이미 84% no-op을 찾아냈다.
2. Layer 1 closed-book / oracle 경로 — 코드 변경이 작고, 품질 실험을 돌릴 가치가
   있는지 자체를 결정한다.
3. Layer 3 지표 — SciFact macro-F1 먼저, NQ 정답 복구 다음.
4. Layer 2 스윕 — 1~3이 "잴 구간이 있다"고 말한 뒤에.
