# 입문 문서 — 이 연구의 방법과 지표

새로 합류한 사람이 회의에서 나오는 말을 알아듣기 위한 문서다. RAG를 처음 접해도
읽을 수 있게 썼고, 설명마다 **우리 프로젝트의 실제 코드와 실측값**을 붙였다.

연구 설계 자체는 `research_proposal.md`, 원 논문 대조는
`implementation_fidelity.md`를 보면 된다.

---

## 0. RAG가 무엇인가

**Retrieval-Augmented Generation.** 언어 모델이 모르는 것을 답하게 하려고,
질문과 관련된 문서를 먼저 찾아서 프롬프트에 붙여주는 방식이다.

```
질문 "ALDH1 발현은 유방암 예후를 나쁘게 하는가?"
   │
   ├─[1] 임베딩 ──────► 질문을 숫자 벡터로 바꾼다 (384개 숫자)
   │
   ├─[2] 검색 ────────► 5,183개 문서 중 벡터가 가까운 3개를 고른다
   │
   ├─[3] 프롬프트 조립► "[근거] 문서1 문서2 문서3 [질문] ... [답]"
   │
   └─[4] 생성 ────────► 언어 모델이 그 프롬프트를 읽고 답을 쓴다
```

우리 시스템의 각 단계 담당은 이렇다.

| 단계 | 담당 | 크기 |
|---|---|---|
| 임베딩 | all-MiniLM-L6-v2 (ONNX) | 90MB |
| 검색 | FAISS `IndexFlatIP` | SciFact 인덱스 10MB |
| 생성 | Gemma 3-270M (llama.cpp, GGUF) | 271MB |
| 재정렬(선택) | bge-reranker-base (ONNX) | 826MB |

**"Advanced RAG 기법"이란 이 네 단계 어딘가에 손을 대서 답을 더 좋게 만들려는
시도들**이다. 본 연구는 그것들이 작은 모델에서도 통하는지를 잰다.

---

## 1. 다섯 가지 기법

각 절은 **무엇을 하는가 → 왜 하는가 → 우리 실측**의 순서다.

### 1.1 Re-ranking (재정렬)

**무엇을 하는가.** 검색을 넉넉히 해서 후보 9개를 가져온 뒤, 별도의 모델로 9개를
다시 채점해 상위 3개만 남긴다.

```
질문 ──► 벡터 검색 ──► 후보 9개 ──► 크로스인코더 채점 ──► 상위 3개 ──► 프롬프트
```

**왜 하는가.** 벡터 검색은 질문과 문서를 **따로따로** 벡터로 만든 뒤 거리를 잰다.
빠르지만 거칠다. 크로스인코더는 `(질문, 문서)` 쌍을 **함께** 읽어서 관련도를
매기므로 훨씬 정확하다. 대신 느려서 전체 문서에는 못 쓰고, 후보를 줄인 뒤에만
쓴다.

**우리 설정.** `rerank_candidate_k: 9` → `top_k: 3`. 채점 모델은
`bge-reranker-base`.

**특징.** 생성 모델을 전혀 쓰지 않는다. 그래서 언어 모델이 아무리 나빠도 이
기법의 성능은 영향을 받지 않는다. **본 연구에서 양성 대조로 쓰기에 좋은 이유**가
이것이다.

### 1.2 MMR (Maximal Marginal Relevance, 다양성 재선택)

**무엇을 하는가.** 상위 k개를 고를 때 관련도만 보지 않고, **이미 고른 것과 얼마나
겹치는지**를 함께 본다.

```
후보 9개에서 3개를 고른다
  1번째: 관련도가 가장 높은 것
  2번째: 관련도가 높으면서 1번째와 내용이 다른 것
  3번째: 관련도가 높으면서 1·2번째와 다른 것
```

수식은 한 줄이다. λ가 둘 사이의 저울이다(1이면 관련도만, 0이면 다양성만).

```
MMR = argmax [ λ · sim(질의, 문서) − (1−λ) · max sim(문서, 이미_선택된) ]
```

**왜 하는가.** 벡터 검색은 질의와 비슷한 것을 위에서부터 고르는데, **비슷한 것들은
서로도 비슷하다.** 그래서 상위 3개가 사실상 같은 내용인 경우가 생긴다. 프롬프트
3칸을 같은 말로 채우면 예산 낭비다.

**우리 데이터에 실제로 있다.** SciFact 300건 중 **41건에서 top-3가 2개 문서로만
채워졌고**(같은 초록의 청크 둘이 뽑힘) 2건은 1개 문서였다. MMR이 줄이려는 중복이
관측된다.

**우리 설정.** λ = 0.5(LangChain·LlamaIndex 기본값), 후보 9개 → 3개. 재정렬과 같은
자리, 같은 후보 풀을 쓴다.

**Re-ranking과의 차이.** 둘 다 "후보 9개에서 3개를 고르는" 기법이지만 기준이 다르다.
**재정렬은 관련도를 더 정확히 재고, MMR은 겹치지 않게 고른다.** 재정렬은 별도
모델(크로스인코더)이 필요하고 MMR은 벡터 계산만 한다.

> **참고: Sentence Window Retrieval은 왜 빠졌는가**
>
> 원래 계획에 있던 기법이다. 문장 하나를 노드로 색인해 정밀하게 검색하고, 넣을
> 때는 앞뒤 문장까지 넓히는 방식이다("검색은 좁게, 컨텍스트는 넓게").
>
> 뺀 이유는 **전용 인덱스를 요구하기 때문**이다. 나머지 기법은 전부 같은 인덱스
> 위에서 동작해 "같은 검색, 다른 후처리"라는 비교가 성립하는데, 이것만 검색
> 자체가 달라진다. 서버가 인덱스를 기동 시점에 고정하므로 모드마다 재기동이
> 필요하고, 입도가 달라 지표도 직접 비교할 수 없다. 자세한 사유는
> `research_proposal.md` §6.1.1에 있다.

### 1.3 Contextual Compression (컨텍스트 압축)

**무엇을 하는가.** 검색된 문서마다 언어 모델에게 "이 문서에서 질문에 답하는 데
필요한 부분만 **원문 그대로** 뽑아라"고 시킨다. 관련 없으면 `NO_OUTPUT`이라고
답하게 해서 그 문서를 통째로 뺀다.

```
문서1 (746자) ──► LLM ──► 관련 부분 발췌 (120자)
문서2 (680자) ──► LLM ──► NO_OUTPUT → 제거
문서3 (590자) ──► LLM ──► 관련 부분 발췌 (95자)
```

**왜 하는가.** 검색 결과의 대부분은 잡음이다. 우리 실측으로 프롬프트 3칸 중
**유용한 건 0.7칸뿐**이다(precision@3 = 23.6%). 잡음을 걷어내면 프롬프트가 짧아져
생성이 빨라지고, 모델이 헷갈릴 여지도 준다.

**중요한 제약.** 원문(LangChain `LLMChainExtractor`)은 **요약이 아니라 발췌**를
요구한다. 프롬프트에 `*AS IS*`(있는 그대로), `*DO NOT* edit`(편집 금지)이 박혀
있다. 요약을 허용하면 모델이 원문에 없는 말을 지어낼 수 있기 때문이다.

**우리 실측.** SciFact 한 건에서 문서 3개 중 1개가 `NO_OUTPUT`으로 제거됐다.
다만 gemma-3-270m이 `No_OUTPUT`이라고 대소문자를 틀리게 써서, 정확히 일치를
검사하면 그 토큰 자체가 근거로 들어가는 문제가 있었다(수정함).

### 1.4 HyDE (Hypothetical Document Embeddings)

**무엇을 하는가.** 질문으로 바로 검색하지 않는다. 먼저 언어 모델에게
**"이 질문에 답하는 가상의 논문 문단을 써봐"**라고 시키고, 그 가상 문단으로
검색한다.

```
질문 "ALDH1 발현은 예후를 나쁘게 하는가?"
   │
   ├─► LLM에게 가상 논문 문단 8개 생성시킴
   │     "ALDH1 발현은 577건 코호트에서 나쁜 예후와..."  ×8
   │
   ├─► 질문 1개 + 가상 문단 8개 = 벡터 9개를 각각 만들고 평균
   │
   └─► 그 평균 벡터로 검색
```

**왜 하는가.** 질문과 문서는 문체가 다르다. 질문은 짧은 의문문이고 문서는 긴
서술문이다. 벡터 공간에서 서로 멀리 떨어져 있을 수 있다. **가상 문서를 만들면
"문서처럼 생긴" 벡터가 되어 진짜 문서 근처에 떨어진다.**

**왜 8개를 평균하는가.** 생성 하나가 엉뚱할 수 있으니 여러 개의 평균으로 오차를
희석한다. 그리고 **원본 질문의 벡터도 평균에 넣는 것이 핵심**이다. 생성이 전부
빗나가도 질문 벡터가 검색을 원래 자리 근처에 붙잡아 주는 앵커 역할을 한다.

**우리 실측 비용.** 쿼리당 **57초**다(생성 8회). `none`이 4초니 **14배**다.
300문항이면 4.75시간. 이 비용 자체가 연구 질문 RQ3의 답이다.

### 1.5 Query Rewriting (질의 재작성)

**무엇을 하는가.** 언어 모델에게 질문을 검색하기 좋은 형태로 다시 쓰게 한다.

```
원본: "A deficiency of vitamin B12 increases blood levels of homocysteine."
재작성: "Vitamin B12 deficiency increases homocysteine levels."
```

**왜 하는가.** 원래는 대화형 질의를 위한 기법이다. "그거 얼마야?" 같은 대명사·
생략이 섞인 질문을 검색 가능한 형태로 펴주는 용도다.

**우리 실측.** SciFact 클레임은 이미 완결된 문장이라 재작성할 여지가 적다.
300건 중 **252건(84%)에서 원본과 글자 하나 다르지 않은 결과**가 나왔고, 실제로
바뀐 경우도 문법 교정·대문자화 수준이었다. 짝지어 비교한 MRR 순효과는 −0.024다.

**이건 구현 결함이 아니라 태스크 부적합일 가능성이 크다.** 논문에는 그렇게
서술하는 편이 정확하다.

## 2. 지표

지표마다 **무엇을 재는가 → 어떻게 읽는가 → 우리 실측 → 함정**의 순서다.

### 2.1 컨텍스트 적중률@k (context hit rate)

**무엇을 재는가.** 정답 근거 문서가 프롬프트에 **들어갔는지 여부**. 질의마다
예/아니오이고, 전체 질의 중 "예"의 비율이다.

**왜 중요한가.** 인과 사슬의 병목이다.

```
근거가 프롬프트에 없다 → 생성기가 아무리 좋아도 맞출 방법이 없다
근거가 프롬프트에 있다 → 이제야 생성기의 능력 문제가 된다
```

**우리 실측 (SciFact, top_k=3).**

```
gold가 1위        152건 (50.7%)
gold가 2위         34건 (11.3%)
gold가 3위         19건 ( 6.3%)
top-3 안에 없음    95건 (31.7%)   ← 개선 여지
──────────────────────────────
적중률            205/300 = 68.3%
```

**읽는 법.** 31.7%는 **검색을 개선하면 채울 수 있는 몫**이다. 이 여지가 넓다는
것은 재정렬이나 HyDE가 효과를 낼 공간이 있다는 뜻이다.

### 2.2 precision@k

**무엇을 재는가.** 프롬프트에 들어간 k개 중 실제로 관련 있는 것의 비율.

**우리 실측.** `precision@3 = 23.6%`. **3칸 중 0.7칸만 유용하다.**

**읽는 법.** 온디바이스에서는 정확도 지표가 아니라 **컨텍스트 예산 효율**로
읽어야 한다. 프롬프트가 길수록 레이턴시가 늘기 때문이다(Qwen3-0.6B 기준 프롬프트
1,000토큰에 11초). Contextual Compression이 겨냥하는 것이 정확히 이 낭비다.

### 2.3 recall@k

**무엇을 재는가.** 정답 근거 전체 중 몇 개나 찾았는지.

**우리 실측.** recall@3 = 66.1%. 적중률(68.3%)과 비슷한 이유는 질의당 gold 문서가
대부분 1개(300건 중 277건)이기 때문이다.

**함정.** 우리는 top_k=3만 검색하므로 **recall@3 = recall@5 = recall@10 = 0.661**로
멈춘다. k를 키워도 값이 안 변한다. 3개 목록에서 10개를 셀 수 없기 때문이다.

### 2.4 nDCG (그리고 왜 주 지표에서 뺐는가)

**무엇을 재는가.** 정답이 순위 목록에서 얼마나 위에 있는지를 **위치 할인**과 함께
잰다. 1위면 만점, 아래로 갈수록 `1/log2(순위+1)`만큼만 인정한다.

**IR 분야의 표준 지표**이고 BEIR 리더보드도 nDCG@10을 쓴다.

**왜 우리 목적에는 안 맞는가.** 위치 할인은 **사람이 검색 결과를 위에서 아래로
훑는 상황**을 모델링한 것이다. 그런데 우리는 문단 3개를 프롬프트에 나란히 붙여
LLM에게 통째로 준다. 3번째 문단이라고 절반만 읽히지 않는다.

**함정 두 가지.**

첫째, 우리 nDCG는 **이진 관련도**다(관련/무관만 있고 등급이 없다). 표준 nDCG와
계산이 다르므로 공개 수치와 그대로 비교하면 안 된다.

둘째, **top_k=3만 검색하는데 nDCG@10을 출력한다.** 실측을 보면 명백하다.

| k | precision | recall | nDCG |
|---|---|---|---|
| 3 | 0.2356 | 0.6612 | 0.5979 |
| 10 | 0.0707 | **0.6612** | **0.5965** |

nDCG@10과 nDCG@3이 사실상 같다. 3개짜리 목록에 대한 값이기 때문이다. **이걸
BEIR 리더보드의 nDCG@10과 나란히 놓으면 잘못된 비교다.**

**결론.** nDCG는 주 지표에서 빼고, 표준 깊이(top-100 이상) 검색을 별도로 돌려
**"우리 검색기가 정상 범위다"를 보이는 용도**로만 쓴다.

### 2.5 macro-F1 (과제 정확도)

**무엇을 재는가.** SciFact의 3지 라벨(SUPPORT / CONTRADICT / NOINFO)을 맞혔는지.
클래스별 F1을 구해 평균한다.

**왜 macro인가.** 단순 정확도를 쓰면 가장 흔한 클래스만 찍어도 점수가 나온다.
macro-F1은 클래스마다 동등한 가중치를 주므로 그런 꼼수가 통하지 않는다.

**현재 상태.** **아직 구현되어 있지 않다.** 지금 파이프라인은 검색 지표(BEIR)와
RAGAS만 산출하고, 라벨 정확도를 재는 경로가 없다. 구축 예정 1순위다.

### 2.6 RAGAS 4지표

LLM을 심판으로 세워 생성 품질을 채점하는 도구다.

| 지표 | 무엇을 재는가 |
|---|---|
| faithfulness | 답변이 주어진 근거에 실제로 기반하는가 (환각 여부) |
| answer_relevancy | 답변이 질문에 대응하는가 |
| context_precision | 검색된 근거가 관련 있는가 |
| context_recall | 검색된 근거가 정답을 덮는가 |

**뒤의 두 개는 BEIR와 중복이다.** 실측 대조다.

| | BEIR (qrels로 정확 계산, 무료) | RAGAS (LLM 심판, 유료) |
|---|---|---|
| none | ndcg@3 **0.598** | context_precision **0.592** |
| none | recall@3 **0.661** | context_recall **0.629** |

소수점 둘째 자리까지 사실상 같다. **같은 것을 더 비싸고 덜 재현 가능하게 재고
있다.** 게다가 비용이 지배적이다 — 300문항 1모드에 4.5~5.0시간이 걸리고 거의
전부가 judging이다. **RAGAS를 빼면 전체 실험이 80시간에서 10시간 이내로 줄어든다.**

앞의 두 개(faithfulness, answer_relevancy)는 생성기를 재는 지표라 의미가 있지만,
**생성기가 컨텍스트에 반응하기 시작한 뒤에야** 정보를 담는다. 부분표본으로 부차
보고한다.

### 2.7 효율 지표

| 지표 | 뜻 | 우리 실측 (gemma-3-270m) |
|---|---|---|
| `model_load` | 모델·인덱스 로딩 시간 | 1,480ms — **총 레이턴시의 39%** |
| `retrieval` | 벡터 검색 | 15~17ms |
| `generation` | 답변 생성 | 3,777ms |
| `output_tokens_per_sec` | 생성 처리량 | 19 tok/s (llama-bench로는 38.5) |
| `memory_mb` (VmHWM) | 피크 메모리 | 805MB |

**`model_load`가 39%인 이유.** 서버가 요청마다 프로세스를 새로 fork해서 모델을
다시 읽는다. 온디바이스 레이턴시를 논문 수치로 쓸 거라면 이 구조를 어떻게
보고할지 정해야 한다.

**VmHWM을 쓰는 이유.** 순간 메모리(VmRSS)는 측정 시점에 이미 해제된 캐시를
놓친다. 피크(VmHWM)가 "이 쿼리가 실제로 필요했던 메모리"다.

## 3. 이 연구만의 방법론 장치 셋

일반적인 RAG 논문에 없는 것들이다. **음성 결과(= 기법이 효과 없다)를 주장하려면
"너희가 잘못 구현/측정했다"는 반박을 먼저 막아야 하고, 셋은 그 장치다.**

### 3.1 기법 실행률 (`technique_effect`)

**문제.** 기법이 조용히 아무 일도 안 할 수 있다. 그런데 기존 계측은 그걸 성공으로
센다.

우리가 실제로 겪은 일이다. `query_rewrite`가 300건 성공을 보고했는데, 실제로는
**252건(84%)에서 원본과 똑같은 질의를 반환**했다. 원인은 이 코드다.

```cpp
if (rewritten.empty()) return {fallback_query, true};   // 빈 출력만 실패로 셈
...
return {rewritten, false};                              // 원본과 같아도 '성공'
```

**해법.** 상태를 넷으로 나눈다.

```
applied         변환이 실제로 무언가를 바꿨다
noop            변환이 입력을 그대로 돌려줬다   ← 기존이 성공으로 세던 것
fallback        변환이 실패해 원본으로 복구했다
not_applicable  이 모드에는 변환 단계가 없다
```

**no-op과 fallback은 결과가 같지만 원인이 정반대다.** 하나는 모델이 일을 안 한
것이고 하나는 방어 로직이 제대로 작동한 것이다. 구분하지 않으면
**"효과 없음"과 "실행 안 됨"을 구분할 수 없다.**

### 3.2 구현 충실도 감사

**문제.** 기법을 원 논문과 다르게 구현해놓고 "효과 없다"고 하면 그건 그 기법에
대한 결과가 아니다.

**우리가 발견한 것.** 감사 전 우리 HyDE는 가상 문서 **1개로 원본 질의를 대체**하고
있었다. 원문은 8개와 원본 질의의 임베딩을 **평균**한다. 앵커 역할을 하는 원본
질의가 통째로 빠져 있었으니 알고리즘이 다른 상태였다.

다섯 기법 전부를 원 논문·공식 구현과 항목별로 대조한 결과가
`implementation_fidelity.md`에 있다. **차이가 남아 있는 부분은 논문에 명시한다.**

### 3.3 closed-book / oracle 기준선

**문제.** `none` 0.5965 → `query_rewrite` 0.599라는 차이가 크다고도 작다고도 말할
수 없다. **분모가 없기 때문이다.**

**해법.** 컨텍스트를 세 조건으로 나눠 잰다.

| 조건 | 생성기에 주는 것 | 의미 |
|---|---|---|
| **closed-book** | 없음 | **바닥** — 검색 없이 모델이 아는 것 |
| retrieved | 실제 검색 결과 | 측정 대상 |
| **oracle** | 정답 근거를 직접 주입 | **천장** — 검색이 완벽할 때 |

효과 크기를 `oracle − closed-book` 대비 비율로 보고한다. 그리고 이 구간이
진단이 된다.

- retrieved ≈ closed-book → **모델이 컨텍스트를 아예 안 쓴다.** 어떤 기법도 무의미
- retrieved ≈ oracle → 검색이 이미 천장. **개선 여지가 없다**
- 구간이 넓을 때만 기법 비교가 의미를 가진다

**실측 예시** (ALDH1 클레임, 정답 = SUPPORTS):

```
closed_book   컨텍스트 0개  "No, the claim is not supported or decidable..."
retrieved     컨텍스트 3개  "The claim is that ALDH1 expression is associated..."
oracle        컨텍스트 1개  "No."
```

세 조건이 다른 답을 내지만 **셋 다 틀렸다.** 좋은 근거를 줘도 맞는 방향으로 가지
않는다는 신호다.

## 4. 자주 나오는 오해

**"파라미터가 270M이니 270M짜리 모델이다"** — 아니다. Gemma 3-270M은 **3분의 2가
262k 어휘의 임베딩 테이블**이고 실제로 계산하는 트랜스포머 본체는 약 100M뿐이다.
SmolLM2-360M은 어휘가 49k라 명목상 비슷한 크기에서 본체가 3.1배 크다. **파라미터
총량이 아니라 본체 크기를 봐야 한다.**

**"검색 점수가 낮으니 검색이 문제다"** — 우리 경우엔 아니다. 근거가 프롬프트
1순위에 들어간 상태에서도 모델이 틀렸다. **검색과 생성 중 어디가 병목인지는
oracle 조건으로 분리해야 안다.**

**"nDCG@10이 0.597이니 리더보드의 0.6대와 비슷하다"** — 아니다. 우리는 3개만
검색하므로 그 값은 3개 목록에 대한 것이다. 리더보드는 top-100 이상을 검색한다.

**"기법을 켰는데 점수가 그대로면 효과가 없는 것"** — 실행됐는지부터 봐야 한다.
`technique_effect`가 `noop`이면 그 쿼리는 baseline과 **똑같은 일**을 한 것이다.

**"양자화 때문에 성능이 나쁜 것"** — 현재 모델은 이미 Q8_0(8.5비트)이라 사실상
원본 정밀도에 가깝다. 그리고 관측된 실패는 정밀도 문제가 아니라 **프롬프트에 먼저
나온 라벨을 그대로 복사하는** 구조적 거동이다.
